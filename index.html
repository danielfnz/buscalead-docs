API da BuscaLead

Acesse nossa base de +71 milhões de empresas brasileiras via API REST. Consulte CNPJs, busque por filtros avançados e enriqueça seus dados - direto no seu sistema. O acesso via API Key requer um plano ativo.

REST

Base URL

https://api.buscalead.com/v1

Autenticação

Todas as requisições autenticadas devem incluir o header Authorization com sua API Key.

Você pode gerar sua API Key na página de configurações da plataforma.

Assinatura obrigatoria: O uso da API via API Key requer uma assinatura ativa. Requisicoes com API Key sem assinatura retornam 402 Payment Required. Assine aqui.

Header de autenticação
Authorization: Bearer sua_api_key_aqui
Exemplo com cURL
curl 'https://api.buscalead.com/v1/empresas/search?query=techsoft' \
-H 'Authorization: Bearer sua_api_key_aqui'

Rate Limiting

A API possui limites de requisições por minuto para garantir estabilidade. Os limites variam conforme o tipo de autenticação.

Tipo Limite Janela
Sem autenticação (busca de empresas) 15 1 minuto
Sem autenticação (demais rotas) 20 1 minuto
Com API Key 60 1 minuto
Rotas de referência (CNAEs, Estados...) 200 1 minuto

Ao exceder o limite, a API retorna 429 Too Many Requests com o tempo restante no header Retry-After.

Webhooks de entrada

POST

Receber leads por webhook

Receba leads de outros sistemas (ERP, site, formulário, CRM) automaticamente. Cada webhook tem uma URL própria e um secret: a cada evento autenticado que o seu sistema envia, o BuscaLead cria ou atualiza o lead na sua organização e garante o card no funil.

/webhook-integrations/{id}/events

URL do webhook

https://api.buscalead.com/v1/webhook-integrations/{id}/events

O {id} é gerado ao criar o webhook. Copie a URL pronta em Configurações → Integrações → Webhooks personalizados.

Planos pagos: webhooks personalizados estão disponíveis nos planos Starter, Plus, Business e Pro. Sem API Key: esta rota não usa o header Authorization; quem autentica a requisição é o secret do webhook, enviado no header X-Webhook-Secret (próxima seção). A assinatura do corpo é uma alternativa opcional.

Como configurar

  1. No BuscaLead, abra Configurações → Integrações e, em Webhooks personalizados, clique em Novo webhook. Apenas proprietário, administrador e gerente da organização criam e gerenciam webhooks.
  2. Dê um nome ao webhook, por exemplo o nome do sistema que vai enviar os leads. Ele aparece na origem de cada lead recebido: Webhook: <nome>.
  3. Copie a URL e o secret. O secret é exibido uma única vez, com 43 caracteres (letras, números, - e _). Se perder, use Regenerar secret: o secret anterior deixa de valer imediatamente.
  4. No seu sistema, envie um POST JSON a cada novo cadastro, com os headers Content-Type: application/json e X-Webhook-Secret: <secret> (o secret exatamente como aparece no painel), como mostra a seção Secret no header. Quer assinar o corpo em vez de enviar o secret? A assinatura opcional (mais segura) também funciona.

O que acontece a cada evento

  • O lead é criado na sua base, ou atualizado se já existir (veja Deduplicação).
  • O card do lead entra na primeira etapa do pipeline padrão da organização.
  • O webhook registra a última recepção, exibida no painel.

Envie sempre do seu servidor. O secret nunca deve aparecer no navegador, em apps ou em repositórios. Teste com dados fictícios: cada evento aceito cria um lead de verdade na sua base.

Enviar com o secret no header

Envie um POST JSON para a URL do webhook com o secret no header X-Webhook-Secret e o BuscaLead processa o evento. É o jeito mais direto e funciona com qualquer sistema que faça um POST com headers: o seu servidor, um curl ou ferramentas como Zapier, Make e n8n. Toda requisição leva dois headers:

Header Valor Obrigatório
Content-Type application/json (pode incluir ; charset=utf-8) Sim
X-Webhook-Secret <o secret, exatamente como aparece> Sim

Passo a passo

  1. Faça um POST para a URL do webhook. Em ferramentas como Zapier, Make e n8n, use a ação de requisição HTTP.
  2. Adicione o header X-Webhook-Secret com o secret copiado do painel (copie e cole, exatamente como aparece).
  3. Envie o corpo como JSON (Content-Type: application/json), no formato da seção Payload. Corpo em formato de formulário ou texto simples é recusado com 422.

Cuide do secret. Ele viaja no header de cada requisição, sempre por HTTPS, mas a ferramenta que envia e os proxies no caminho podem registrar os headers em logs. Se suspeitar que o secret foi exposto, use Regenerar secret: o anterior deixa de valer imediatamente. Quer que o secret nunca viaje? Veja Opcional: assinatura (mais segura).

Exemplo em bash (curl)
URL='https://api.buscalead.com/v1/webhook-integrations/SEU_ID/events' SECRET='SEU_SECRET' curl -i -X POST "$URL" \ -H 'Content-Type: application/json' \ -H "X-Webhook-Secret: $SECRET" \ --data-binary '{"company":{"cnpj":"12345678000190","razao_social":"Empresa Exemplo"},"contact":{"name":"Maria","email":"maria@exemplo.com","phone":"11987654321"},"extra":{"origem":"site"}}'

Opcional: assinatura (mais segura)

Se o seu sistema puder, em vez de enviar o secret você pode assinar cada requisição: o secret fica guardado com você e só a assinatura viaja. A assinatura também prova que o corpo veio de quem conhece o secret e que não foi alterado no caminho. Neste modo, toda requisição leva dois headers (no lugar do X-Webhook-Secret):

Header Valor Obrigatório
Content-Type application/json (pode incluir ; charset=utf-8) Sim
X-Webhook-Signature sha256=<assinatura em hexadecimal> Sim

Qual header vale

Se a requisição trouxer X-Webhook-Signature (com qualquer valor), só a assinatura é conferida: um X-Webhook-Secret correto não corrige uma assinatura errada. Sem X-Webhook-Signature, vale o X-Webhook-Secret. Sem nenhum dos dois, a resposta é 401.

Como calcular

  1. Monte o corpo JSON como texto (string) uma única vez.
  2. Calcule o HMAC-SHA256 desse corpo, usando o secret como chave, e converta o resultado para hexadecimal (64 caracteres, em maiúsculas ou minúsculas).
  3. Envie o resultado no header X-Webhook-Signature, com o prefixo sha256= em minúsculas.
  4. Envie no corpo exatamente o mesmo texto que foi assinado.

Dois detalhes que mais causam 401:

  • Use o secret exatamente como aparece (copie e cole). Ele é a chave do HMAC, sem nenhuma conversão.
  • Assine os bytes exatos que você envia. Se o seu cliente HTTP reserializar o JSON depois de assinado (espaços, ordem das chaves, escape de acentos), a assinatura deixa de bater. Gere o texto, assine e envie esse mesmo texto.
Exemplo em Node.js 18+ (enviar-lead.mjs)
import { createHmac } from 'node:crypto'; const URL_DO_WEBHOOK = 'https://api.buscalead.com/v1/webhook-integrations/SEU_ID/events'; const SECRET = process.env.BUSCALEAD_WEBHOOK_SECRET; // texto do secret, exatamente como exibido // Serialize UMA vez: assine e envie exatamente esta mesma string. const body = JSON.stringify({ company: { cnpj: '12345678000190', razao_social: 'Empresa Exemplo' }, contact: { name: 'Maria', email: 'maria@exemplo.com', phone: '11987654321' }, extra: { origem: 'site' }, }); const assinatura = createHmac('sha256', SECRET).update(body).digest('hex'); const resposta = await fetch(URL_DO_WEBHOOK, { method: 'POST', headers: { 'Content-Type': 'application/json', 'X-Webhook-Signature': `sha256=${assinatura}`, }, body, }); console.log(resposta.status, await resposta.text());
Exemplo em bash (openssl + curl)
URL='https://api.buscalead.com/v1/webhook-integrations/SEU_ID/events' SECRET='SEU_SECRET' BODY='{"company":{"cnpj":"12345678000190","razao_social":"Empresa Exemplo"},"contact":{"name":"Maria","email":"maria@exemplo.com","phone":"11987654321"},"extra":{"origem":"site"}}' SIGNATURE=$(printf '%s' "$BODY" | openssl dgst -sha256 -hmac "$SECRET" | awk '{print $NF}') curl -i -X POST "$URL" \ -H 'Content-Type: application/json' \ -H "X-Webhook-Signature: sha256=$SIGNATURE" \ --data-binary "$BODY"

Payload

O corpo é um JSON com três blocos opcionais: company, contact e extra. É obrigatório informar ao menos um identificador (CNPJ, e-mail ou telefone).

Campo Tipo Regras
company.cnpj string 14 dígitos. Pontuação é aceita e removida (12.345.678/0001-90)
company.razao_social string 1 a 255 caracteres
company.nome_fantasia string 1 a 255 caracteres
contact.name string 1 a 255 caracteres
contact.email string E-mail válido, até 254 caracteres
contact.phone string DDD + número, de 10 a 13 dígitos. Formatação é aceita. Recomendamos enviar com o código do país (5511987654321)
extra object Objeto livre (chaves e valores à sua escolha), até 10.000 bytes de JSON. Gravado quando o lead é criado

O contrato é estrito:

  • company aceita somente cnpj, razao_social e nome_fantasia. contact aceita somente name, email e phone. A raiz aceita somente company, contact e extra.
  • Qualquer outra chave, em qualquer um desses níveis, é recusada com 422. Dados adicionais vão em extra.
  • Informe ao menos um entre company.cnpj, contact.email e contact.phone.
  • Para não enviar um campo ou bloco, omita a chave: null não é aceito. O extra precisa ser um objeto (não lista nem texto).
  • O corpo inteiro pode ter no máximo 256 KB (262.144 bytes).
Exemplo de corpo
{ "company": { "cnpj": "12345678000190", "razao_social": "Empresa Exemplo", "nome_fantasia": "Exemplo" }, "contact": { "name": "Maria", "email": "maria@exemplo.com", "phone": "11987654321" }, "extra": { "origem": "site", "plano": "premium" } }
Resposta - 422 (chave não aceita em contact)
{ "error": "Payload inválido", "details": [ { "code": "unrecognized_keys", "keys": ["cargo"], "path": ["contact"], "message": "Unrecognized key: \"cargo\"" } ] }

details lista cada problema: path aponta o campo e message explica o motivo.

Deduplicação e atualização

Reenviar o mesmo cliente é seguro: o BuscaLead atualiza o lead existente em vez de duplicar e nunca cria um segundo card para o mesmo lead.

Como o lead é encontrado

A busca acontece dentro da sua organização, nesta ordem:

  1. CNPJ (company.cnpj), se enviado.
  2. Telefone (contact.phone), com ou sem o nono dígito, no telefone 1 ou 2 do lead. Havendo mais de um lead, vale o mais antigo.
  3. E-mail (contact.email), por igualdade exata (diferencia maiúsculas e minúsculas, então envie sempre em minúsculas). Havendo mais de um lead, vale o mais antigo.

Se o evento traz um CNPJ e o lead encontrado por telefone ou e-mail já tem outro CNPJ, ele é tratado como outra empresa e a busca segue adiante. Lead encontrado sem CNPJ pode ser enriquecido com o CNPJ do evento.

O que é gravado

Situação Resultado
Lead não encontrado Cria o lead com os campos enviados. A origem fica Webhook: <nome do webhook> e o extra é guardado na atribuição do lead.
Lead encontrado Atualiza apenas os campos enviados (CNPJ, razão social, nome fantasia, nome do contato e e-mail). O que você não enviou permanece como está. Origem e extra não são regravados.
Telefone enviado Salvo normalizado, com código do país (55) e nono dígito nos celulares. Se o número já está no lead, nada muda. Se é um número novo, passa a ser o telefone principal do lead.
Card no funil Um card por lead, na primeira etapa do pipeline padrão. Se o card já existe, ele é reaproveitado. Se a organização não tem pipeline padrão, o lead é gravado e card_id volta null.

Respostas, limites e retentativas

Resposta - 200 OK
{
"success": true,
"lead_id": "b3f5c1d2-0a4e-4c8b-9f6d-2e7a1c5d8b90",
"card_id": "7d2e9a40-51cb-4f3a-8e16-c04b9d7a3f25"
}

Neste endpoint, o corpo dos erros pode ser {"error": "..."} ou o formato geral da seção Erros. Decida sempre pelo código HTTP.

Código Quando O que fazer
200 Evento processado: lead criado ou atualizado. card_id é null se a organização não tem pipeline padrão. Nada. Marque o evento como entregue.
400 O corpo não é um JSON válido. Corrija o JSON. Reenviar igual repete o erro.
401 URL inexistente (ou com um id que não é UUID), webhook desativado, nenhuma credencial (nem X-Webhook-Secret nem X-Webhook-Signature), secret ou assinatura inválidos, ou, ao assinar, Content-Type de texto/formulário (o corpo não pode ser assinado). Todas as causas respondem igual ({"error":"Unauthorized"}). Confira a URL, se o webhook está ativo e o header X-Webhook-Secret (o secret exatamente como aparece no painel). Se você assina o corpo, confira a assinatura sobre o corpo exato. Eventos enviados com o webhook desativado não são reprocessados.
413 Corpo acima de 256 KB (262.144 bytes), qualquer que seja o Content-Type. Reduza o corpo, principalmente o extra.
415 Content-Type sem suporte (por exemplo application/xml) ou corpo enviado sem Content-Type. Envie Content-Type: application/json.
422 Autenticação válida, mas o conteúdo está fora do contrato (por exemplo: chave não aceita, nenhum identificador, CNPJ sem 14 dígitos, telefone fora de 10 a 13 dígitos, e-mail inválido, texto acima do limite, caractere nulo (\u0000) ou Unicode inválido (surrogate solitário, como \ud83d sem o \ude00) em qualquer texto ou chave, extra acima de 10.000 bytes, ou, ao enviar o secret no header, corpo que não é JSON, como formulário ou texto). Veja details. Corrija conforme details.
429 Limite excedido: mais de 140 requisições por minuto neste webhook ou mais de 600 por minuto vindas do mesmo IP. Aguarde e reenvie com espaçamento crescente. Respeite o header Retry-After quando houver. Insistir acima do limite por IP pode bloquear o IP por 10 minutos.
5xx Falha temporária do servidor. Reenvie com espaçamento crescente.

Limites

Limite Valor
Requisições por webhook 140 por minuto
Requisições por IP (todos os webhooks somados) 600 por minuto
Tamanho do corpo 256 KB
Tamanho do extra 10.000 bytes

Retentativas

  • Reenvie apenas 429 e 5xx, esperando um pouco mais a cada tentativa (por exemplo 1 s, 2 s, 4 s, 8 s...).
  • Os demais códigos (400, 401, 413, 415 e 422) pedem correção antes de reenviar.
  • Reenviar um evento é seguro: o lead é atualizado, nunca duplicado, e o card não é recriado.
  • Toda requisição autenticada conta no limite por webhook, inclusive as recusadas com 422.
